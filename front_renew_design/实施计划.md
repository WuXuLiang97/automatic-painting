# 前端自动刷图客户端实施计划（front）

> 目标：在**不影响现有使用**的前提下，分小步优化 `front`，每完成一个小点都能启动客户端并跑完整流程。

---

## 一、实施原则

1. **可运行优先**：任何阶段结束后，`python front/app.py` 必须能正常启动登录界面并进入主界面完成一次刷图（或模拟刷图）。
2. **小步快跑**：每个任务控制在 0.5–3 小时内完成，改动范围尽量局部。
3. **先修复后重构**：优先修明显 bug 与潜在崩溃点，再做结构优化。
4. **单点回滚**：每个任务修改尽量集中在少数文件；一旦发现问题可以只回退当前任务的改动。

---

## 第二阶段之前的准备工作（当前基线）

> 假设当前基线是你现在使用的 front 版本（已能正常登录 + 连接服务端 + 正常刷图）。

**准备动作：**

- 建议建立一个单独的 Git 分支，如 `front-refactor`；
- 每完成文档中的一个「任务」就 commit 一次，message 写明对应小节编号，便于回滚。

## 第一阶段：显式 bug 修复与运行稳定性（高优先级）

### 1.1 登录 / 修改密码错误处理修正

**优先级：** ⭐⭐⭐⭐⭐  
**风险：** 低（逻辑修正，不改变协议）  
**主要文件：** `app.py`, `utils/api.py`

**任务内容：**

1. **修复登录失败时的 `None.get()` 崩溃：**
   - 在 `LoginPage.login` 中：  
     - 将判断逻辑改为：`if ret is not None:` 视为登录成功，否则统一提示“用户名或密码错误/网络错误”；  
     - 不再在 `else` 分支中访问 `ret.get(...)`。
2. **修改密码流程健壮性：**
   - 在 `ChangePasswordPage.change_password` 中：  
     - 调用 `test_login` 后，若返回 `None`，直接弹出“旧密码错误或网络异常”，不再继续调用 `test_change_password`；  
     - 对 `test_change_password` 返回值增加类型检查，`not isinstance(ret, dict)` 时提示“服务器返回异常”。

**如何测试（必须都通过）：**

1. 启动服务端（当前你线上使用的那一套）；
2. 运行 `python front/app.py`；
3. 执行以下场景：
   - 输入错误密码登录：应弹出友好错误提示，程序不崩溃，仍可再次尝试登录；
   - 输入正确账号密码登录：应正常进入主界面；
   - 修改密码时，旧密码错误：应提示错误，程序不崩溃；
   - 修改密码成功后，尝试登录新密码：应成功。

**通过标准：**

- ✅ 所有上述场景中，界面无卡死/无崩溃；
- ✅ 日志中能看到相应错误信息，但不出现 Traceback 异常（除非为 debug 特意保留）。

### 1.2 截图与 YOLO/OCR 失败时的安全兜底

**优先级：** ⭐⭐⭐⭐  
**风险：** 低（只加 guard，不改正常路径）  
**主要文件：** `utils/screenshot_util.py`, `core/player.py`, `core/playerHelper/socket_Handler.py`

**任务内容：**

1. **明确 `get_game_screenshot` 的失败行为：**
   - 在 `ScreenshotUtil.get_game_screenshot` 中：  
     - 在超过 `max_retry` 或 `timeout` 后，记录日志，并返回 `None`（而不是隐式结束函数）；  
     - 不要在这里抛未捕获异常。
2. **在使用截图的地方增加判空与跳过当前循环：**
   - `core/player.py` 中所有调用 `screenshot_util.get_game_screenshot()` 的地方：  
     - 如果返回 `None`：  
       - 输出一条日志（如“截图失败，本轮循环跳过”）；  
       - `time.sleep(短时间)` 后 `continue`，避免后续对 `None` 做 `cv2.cvtColor` 或切片。
3. **YOLO/OCR 网络调用兜底：**
   - 在 `SocketHandler.get_yolo_res` / `get_text` / `get_min_map_yolo_res` 中，保留已有异常捕获；  
   - 确保异常发生时返回 `False` 或空字符串，调用方必须检查返回值而不是假定一定成功。

**如何测试：**

1. 正常运行一次完整刷图，看功能不受影响；
2. 手工制造异常（任选其一即可）：  
   - 在游戏窗口最小化/关闭后启动脚本：应在日志中多次提示截图失败，但程序不崩溃；  
   - 暂时停止 YOLO/OCR 服务端：应看到识别失败日志，但主线程仍然能继续循环（可能只是站街或不停尝试）。

**通过标准：**

- ✅ 在游戏/服务端不可用的情况下，前端不会崩溃，只会反复记录失败并“空转”；  
- ✅ 恢复游戏/服务端后，无需重启前端即可恢复正常工作（如果当前逻辑允许）。

## 第二阶段：HTTP API 封装与 UI 去阻塞（中高优先级）

### 2.1 抽象认证服务层（AuthService）

**优先级：** ⭐⭐⭐⭐  
**风险：** 中（涉及接口调用路径）  
**主要文件：** `app.py`, `utils/api.py`

**任务内容：**

1. 在 `utils/api.py` 中新增一个轻量级的 `AuthService`（或者一组函数），统一包装：
   - `login(username, password) -> (success: bool, cookies, error_msg: str)`；
   - `register(username, password) -> (success: bool, error_msg: str)`；
   - `change_password(cookies, old_pwd, new_pwd) -> (success: bool, error_msg: str)`.
2. 这些函数内部调用原来的 `test_login/test_register/test_change_password`，先不改协议，只做结果包装。
3. 修改 `app.py` 中登录/注册/改密页面逻辑，改用新的封装，而不是直接用 `test_*`。

**如何测试：**

- 重复第一阶段中的所有登录/注册/改密测试用例；
- 日志检查：确认不再出现 “`RequestsCookieJar` 被当作 dict 使用” 等误用。

**通过标准：**

- ✅ 登录/注册/改密功能与之前行为一致或更友好；  
- ✅ UI 代码中不再直接使用 `test_login/test_register/test_change_password`。

---

### 2.2 登录/注册改为后台线程调用（避免 UI 卡死）

**优先级：** ⭐⭐⭐⭐  
**风险：** 中（UI 交互路径调整）  
**主要文件：** `app.py`

**任务内容：**

1. 为登录/注册/改密各自增加一个简单的 Worker：
   - 可以用 `QThread` + 自定义信号，或 `QtConcurrent.run` + 回调；
   - Worker 只调用 `AuthService` 中的方法，并将结果通过信号发回主线程。
2. 在 UI 层（按钮点击时）：
   - 禁用按钮（防止重复点击）、显示“正在登录/注册…”的状态提示；
   - 收到 Worker 信号后恢复按钮、根据 success/error 更新界面。

**如何测试：**

1. 启动前端，断开网络或临时关闭后端；
2. 点击“登录”：
   - UI 不应立刻卡死，按钮会变灰，稍后出现错误提示；
   - 整个窗口仍可被拖动/关闭；
3. 恢复网络或后端，再次尝试登录，能正常成功。

**通过标准：**

- ✅ 无论网络是否正常，点击登录/注册都不会卡死整个窗口；  
- ✅ 登录过程中的所有异常都通过对话框或状态提示反馈给用户。

### 3.2 收紧 `global_variable` 的使用范围（第一步：只读化关键值）

**优先级：** ⭐⭐⭐  
**风险：** 中（容易遗漏某个写入点）  
**主要文件：** `core/global_variable.py` 及所有引用处

**任务内容：**

   - 给 `core/global_variable.py` 中重要变量（`banzhuan/sy/tab_index/server_ip/server_port` 等）添加注释，说明**谁负责写入，谁只读**；


**如何测试：**

**通过标准：**

- ✅ 功能无变化；  
- ✅ 全局变量的读写点数量没有增加，为后续“去全局化”打下基础。

## 第四阶段：核心逻辑渐进解耦（低风险小步）

> 这一阶段的目标是**给未来的重构铺路**，不在短期内彻底推翻现有结构。

### 4.1 抽出 YOLO 结果解析的纯函数层

**优先级：** ⭐⭐⭐  
**风险：** 中  
**主要文件：** `core/playerHelper/yolo_Handler.py`, `core/player.py`

**任务内容：**

1. 确保 `YoloHandler.process_detect_message` / `min_map_process_detect_message` 的输入输出是纯数据结构（`context` 只提供只读信息，比如地图名、玩家职业等）；
2. 确保「修改 context」的逻辑只存在于 `apply_to_context` / `min_map_apply_to_context` 中：
   - 在 `PlayerThread` 中调用时，改为：

   ```python
   result = self.yolo_handler.process_detect_message(self, cls, game_image)
   self.yolo_handler.apply_to_context(self, result)
   ```

3. 避免在 `process_detect_message` 内部直接读写 `context.doorOpenState` / `room_item_pickup_counts` 等状态。

**如何测试：**

- 启动脚本，观察：
  - 正常刷图流程：识别怪物、门、奖励行为是否与之前一致；
  - 日志中打印的 `result.goods/doord/monsters/is_boss` 等是否符合预期；
  - 手动对比前后两个版本的关键日志（如 doorOpenState 变化）。

**通过标准：**

- ✅ 行为与重构前一致（或只存在可接受的小差异）；  
- ✅ `YoloHandler` 中对 `context` 的直接写操作明显减少，主逻辑集中到 `apply_to_context`。

### 4.2 抽出技能控制策略骨架

**优先级：** ⭐⭐⭐  
**风险：** 中  
**主要文件：** `utils/skill_util2.py`, `core/player.py`

## 结语：如何使用本计划

- **建议顺序：** 按章节从上到下执行（1.x → 2.x → 3.x → 4.x），其中 1.x 和 2.x 部分对你当前“日常使用稳定性”提升最大；
- **每个任务完成后：**
  - 至少完成一轮「启动 → 登录 → 进入主界面 → 开始一次刷图（或模拟）→ 停止」的手动测试；
  - 如果你有时间，可以为高风险改动配一两个小的自动测试脚本（例如对截图、YOLO/OCR 的简单调用验证）。

整个实施计划是为「不耽误你用」设计的：  
任何时候发现问题，都可以退回到上一个任务结束时的 commit，前端依旧是可用的。后续如果你愿意，我可以基于这些任务再帮你设计对应的小测试脚本（例如前端自测脚本或简单的 UI 自动化）。
