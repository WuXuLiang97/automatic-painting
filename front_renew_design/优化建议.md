## 前端自动刷图客户端优化建议（front）

> 基于对 `front` 目录下全部代码（登录/主界面/UI 配置/自动刷图逻辑/YOLO+OCR/硬件控制等）的完整梳理，给出整体优化方向与分阶段实施建议。

---

## 一、整体评估与目标

- **整体情况**：功能非常完整（登录注册、配置组与角色配置、VNC/采集卡接入、自动刷图、YOLO+OCR 识别、技能释放等），但长期演进后存在明显“堆积式”代码与强耦合问题。
- **当前主要问题**集中在：
  - 核心线程 `PlayerThread` 职责过重、代码体量过大，难以维护和测试；
  - 各模块通过全局变量、单例和硬编码强耦合（`gv`, `screenshot_util`, `vnc_mm`, `pyauto` 等）；
  - 登录/配置等业务直接在 UI 线程发 HTTP 请求，缺少统一的 API 封装与错误处理；
  - 配置读取/键位映射存在重复实现；安全性（本地密码存储、HTTP 明文）和异常处理较弱。

**整体优化目标：**

- 在不破坏现有功能的前提下，逐步：
  - 降低核心模块的复杂度和耦合度；
  - 提升错误处理与运行稳定性（避免“偶发死锁/假死/崩溃”）；
  - 为后续功能新增和自动化测试打基础。

---

## 二、架构与模块边界问题

### 1. `PlayerThread` 过大且职责混杂  ⚠️ 高优先级

**现状：**

- `core/player.py` 中 `PlayerThread` 超过 3000 行，内部同时承担：
  - 业务主循环（搬砖/剧情模式切换等）；
  - 网络通信（YOLO / OCR 服务器的连通性与请求）；
  - 图像获取与小地图解析（通过 `screenshot_util`、`miniMapUtil`）；
  - 怪物/门/奖励识别与行为决策（调用 `YoloHandler`、寻路逻辑等）；
  - 技能系统控制（`skill_util`、`MovementRecorder`、`OperatorModule` 等）；
  - 状态监控（`PlayerStateMonitor`）、计时与“长休息”策略。

**问题：**

- 高度内聚所有逻辑，任何一个小改动都可能影响多处行为，难以定位 bug。
- 几乎无法进行单元测试或局部重构，只能依赖“整套游戏环境 + 服务端”联调。

**建议拆分方向：**

- 引入更清晰的领域服务/组件边界：
  - `GameSession`：负责一次刷图会话生命周期和高层状态机；
  - `VisionService`：封装截图、YOLO/OCR 调用与结果缓存；
  - `NavigationService`：封装小地图、`a_star` 寻路与房间状态管理；
  - `SkillService`：封装技能识别结果与释放策略（包括 boss 与普通模式分支）；
  - `ConfigService` / `ConfigurationManager`：负责从后端读取/更新角色配置。
- `PlayerThread` 只保留「调度与容错」逻辑，具体行为委托给上述组件。

> **实施建议：** 短期内不强求完全切分，可以先将“YOLO 结果解析”“小地图逻辑”“技能控制”三个大块抽出去，形成独立类，再被 `PlayerThread` 持有调用。

---

### 2. 全局状态与单例滥用

**现状：**

- `core/global_variable.py` 中定义大量全局变量（`server_ip/server_port/banzhuan/sy/tab_index/identifier/display_queue` 等），并在多处直接引用。
- `screenshot_util`、`vnc_mm`、`miniMapUtil`、`pyauto`、`socket_handler` 等都以模块级单例存在。

**问题：**

- 修改任意一个全局变量，其他模块行为立刻受到影响，很难追踪来源；
- 阻碍单元测试与分层：测试时不得不准备完整的 Windows + 游戏 + 服务器环境；
- 更换实现（例如替换截图/YOLO 通信方式）成本很高。

**建议：**

- 对关键依赖改用“构造函数注入/显式传递”：
  - 例如在 `PlayerThread.__init__` 中接受 `screenshot_service`, `vision_service`, `input_controller` 等实例，而不是在函数内部直接引用模块级单例；
  - 将 `gv` 用作“参数默认来源”，而不是唯一事实来源——在新代码中优先通过对象属性获取。
- 新增一层 `Context`/`AppEnvironment` 对象，集中管理：
  - 服务器地址、模式（搬砖/剧情）、硬件配置（采集卡/VNC/YJS）；
  - 统一传给需要的模块，减少裸用全局变量的地方。

---

### 3. 配置读取逻辑重复与耦合

**现状：**

- `core/Config.py` 中有一套 `default_config + CONFIG_PATH + get_gui_config/get_key_config`；
- `core/callMain.py` 开头又写了一份 `get_gui_config`（部分字段重复但不完全一致）。

**问题：**

- 配置语义不统一，后期增加字段很容易只改了一处，导致行为不一致；
- 键位配置既出现在 `Config`，也出现在 UI（`KeyConfigDialog`、`SkillUtil`）中，存在重复解析逻辑。

**建议：**

- 将 GUI/按键配置的**唯一入口**统一到 `core/Config.py`：
  - 所有读取配置的地方都 `from core.Config import get_gui_config, get_key_config`；
  - 删除 `callMain.py` 里重复的 `get_gui_config`；
  - 文档化现有配置字段的含义（`vmware_ip`, `weak_setting`, `wait_seconds` 等）。
- 针对按键配置，约定统一的 key 表示规范：
  - 存储层：使用统一格式（如 `'Q'`, `'Ctrl+Q'`）；
  - 输入层 (`pyauto`/YJS)：单独维护“UI 文本 → 物理键位”的映射表，避免在各处手动 `lower()` 或 `split('+')`。

---

## 三、HTTP API 与登录/配置管理

### 1. 登录/注册/改密错误处理缺失  ⚠️ 高优先级

**典型问题：**

- 登录失败时 `test_login` 返回 `None`，但 `LoginPage.login` 在 `else` 分支中仍然调用 `ret.get("message")`，直接触发异常。
- 修改密码流程中，未判断旧密码登录是否成功（`cookies is None`），仍然调用 `test_change_password` 并假定返回 JSON。

**建议：**

- 调整 `utils/api.py` 中对外暴露的函数，统一返回结构，例如：

  ```python
  {"ok": True, "data": {...}, "error": None}
  ```

  或：

  ```python
  success, data, error = api_login(username, password)
  ```

- UI 层只依赖这个统一协议，不再直接操作 `requests.Response` 或 `cookies`，所有 HTTP 异常（超时/网络错误/非 JSON 响应）在 API 层屏蔽并转为可展示的 `error` 文本。

### 2. UI 线程同步网络调用

**现状：**

- 登录、注册、修改密码、配置组/角色设置管理等均在主线程直接调用 `requests`。

**问题：**

- 后端延迟或网络抖动时，整个窗口会“假死”，用户无法操作；
- 连续多次网络异常时，容易出现 UI 无响应甚至崩溃。

**建议：**

- 增加简单的“API Worker 线程”层：
  - 使用 `QThread` 或 `QtConcurrent` 将具体网络调用放到后台；
  - 主线程只处理：禁用/恢复按钮、展示 loading、在返回信号中更新 UI。
- 在 `utils/api.py` 中为所有 `requests` 添加超时与异常捕获（例如 `timeout=5`），防止挂死。

### 3. “测试接口”与“正式接口”混用

**现状：**

- `utils/api.py` 中函数全部命名为 `test_xxx`，内部打印大量调试信息（`print_response`），但已经在正式登录/配置功能中使用。

**建议：**

- 将“正式 API”重命名并抽取到清晰的接口层，例如：
  - `api_login`, `api_register`, `api_change_password`, `api_list_subgroups` 等；
  - 测试逻辑（如 `run_tests()`）单独放到 `api_test.py` 或测试脚本，不与生产代码混杂。

## 四、线程与资源管理

### 1. 截图与 VNC/采集卡资源管理

**问题：**

- `ScreenshotUtil.get_game_screenshot` 在多次失败或超时后未有明确返回值/异常约定，调用方通常默认其成功，后续使用时可能在 `cv2.cvtColor`、数组切片处崩溃。
- `CaptureCardConnection.start_preview` / `VNC.capture` 等内部有无限循环，错误处理时只 `logger`，调用方缺少统一的关闭接口和状态检查。

**建议：**

- 定义统一的“截图服务”接口，例如：

  ```python
  class ScreenshotService:
      def capture(self) -> np.ndarray | None: ...
  ```

  并约定：返回 `None` 即代表捕获失败，调用方必须显式判空。

- 对 `ScreenshotUtil.get_game_screenshot`：
  - 在超时后直接抛自定义异常，或返回 `None`；
  - 所有使用处先判断，再决定是否重试/退出本轮循环。

### 2. 线程停止/退出协议不统一

**问题：**

- 不同线程采用不同机制：`self.running` 标志、`STOP_EVENT`、`QThread.wait()` 等；
- 某些循环中异常未被捕获，会直接导致线程 silently crash。

**建议：**

- 约定统一的停止协议：
  - 每个长期运行线程类提供 `stop()` 方法，内部设置标志并做必要的清理；
  - 在主窗口退出前，统一依次调用各线程的 `stop()` + `wait()`，确保有序关闭。
- 在核心循环中（如 `PlayerThread.run`）增加顶层 `try/except`，记录异常并安全停止，而不是让异常冒泡导致线程直接终止。

## 五、图像识别 / 地图 / 技能系统

### 1. 图像识别模块职责收敛

**现状：**

- `YoloHandler` 同时：
  - 解析 YOLO 结果并生成 `YoloProcessResult`；
  - 直接修改 `context.doorOpenState`、`context.room_item_pickup_counts` 等运行时状态。
- `MiniMapUtil` 既做截图坐标计算，又做模板匹配，还在文件底部包含图片去重工具脚本。

**问题：**

- 语义边界模糊，难以复用/测试单个功能；
- 工具性脚本（图片去重）与核心逻辑混杂在同一文件中，增加理解成本。

**建议：**

- 保持 `YoloHandler` 的“纯净性”：只负责“输入 YOLO 结果 → 输出结构化状态 (result)”，不直接修改外部 context；
- 将“把 `result` 应用到 context”这一步集中到 `apply_to_context` 这种方法中，由上层显式调用；
- 将与运行时无关的工具函数（如 `remove_duplicate_images`、图像 hash 等）移到单独的工具脚本或 `tools/` 目录。

### 2. 地图配置与魔法数集中管理

**现状：**

- 各种地图名、房间网格尺寸、BOSS 高度、房间最少数量等散落在多个文件（`common.py`, `minimap_util.py`, `YoloHandler` 等）中，全部是硬编码字典。

**问题：**

- 新增/调整地图时需要在多文件多处同步修改，容易漏改；
- 同一地图在不同模块中的视图不一致（名字、难度、房间结构等）。

**建议：**

- 引入统一的“地图配置中心”（可以是 JSON/YAML 或一个专门的 `maps.py`）：
  - 每个地图定义集中在一处：显示名称、内部 ID、房间网格、最小房间数、BOSS 高度信息等；
  - 其他模块只引用这个配置，不再自己写硬编码。

### 3. 技能系统结构化

**现状：**

- `SkillUtil` 同时负责：
  - 根据 `key_config.json` 把技能槽位映射到按键；
  - 从 UI 截图中裁剪技能图块，判断是否冷却结束；
  - 决定释放顺序（普通模式/BOSS 模式/特殊位移技能）。

**建议：**

- 将技能逻辑拆分为：
  - `SkillLayout`：描述技能槽布局（每个槽位的屏幕区域）；
  - `SkillDetector`：输入当前画面，输出“哪些技能可用”的布尔列表；
  - `SkillPolicy`：根据职业、敌人情况、模式（Boss/普通）选择要释放的技能键；
  - `SkillConfig`：从 `key_config.json` 读取键位配置，负责 “槽位 → 键位” 映射。

这样可以方便：

- 单独测试“技能识别是否准确”；
- 单独迭代“技能释放策略”（例如不同职业不同优先级）。

## 六、UI 层（PyQt）与交互细节

### 1. UI 与业务逻辑解耦

**问题：**

- `RoleSettingsWindow`、`SettingsGroupWindow`、`AuthApp/LoginPage` 均直接调用 `utils.api` 并拼接/解析 JSON；
- 主窗口 `AppMain` 内部直接处理线程控制/网络连接/状态机，UI 与业务紧密耦合。

**建议：**

- 引入简单的“服务层”：
  - `AuthService`：封装所有登录/注册/改密逻辑；
  - `ConfigService`：封装配置组与角色配置的增删改查；
  - UI 只调用这些服务层，并使用信号/槽或回调接收结果。
- 对长时间操作（网络请求/大图像处理），在 UI 上给出明确反馈：
  - 禁用按钮、防止重复点击；
  - 状态栏或弹窗展示错误信息，而不是仅写日志。

### 2. 键位配置与实际按键发送的一致性

**问题：**

- `KeyConfigDialog` 中使用的是用户友好的按键名称（如 `Ctrl+Q`、`Space`），而 `pyauto` / `YJS` 层期待的是内部编码（如 `'q'`, `'space'` 等），中间转换逻辑分散在多处。

**建议：**

- 定义一个统一的“按键映射表”模块，例如：

  ```python
  # key_mapping.py
  UI_TO_INTERNAL = {
      "Q": "q",
      "Space": "space",
      "Ctrl+Q": "q",  # 控制组合键语义时另行处理
  }
  ```

- `SkillUtil` 和动作模块统一通过该映射转换，而不是在各自模块中手动 lower/split。

## 七、安全性与部署

### 1. 本地密码与记住登录

**现状：**

- “记住密码”采用 Base64 简单编码，并将用户名/密码/自动登录标志写入本地 JSON 文件。
- 本地 `users.json` 保存的是明文密码。

**建议：**

- 如果要提升安全性：
  - 至少对密码进行不可逆 hash 存储（登录时只发送明文到服务端，不在本地保留）；
  - 或采用对称加密 + 本地固定密钥（防君子不防小人级别）。
- 尽量不在本地长期保存明文密码；自动登录可通过服务端发放长期 token 实现。

### 2. HTTP 明文与网络错误

**现状：**

- 所有接口使用 `http://` 明文传输，且缺乏统一的超时与重试机制。

**建议：**

- 有条件时将后端改为 HTTPS（至少内网/公网部署时）；
- 在客户端端增加合适的 `timeout` 与重试策略，并对网络错误给出用户可理解的提示（不是简单崩溃或无响应）。

---

## 八、分阶段实施建议（路线图）

### 阶段 1：止血与稳定性提升（优先）

- 修复登录/修改密码等明显的 `None.get()` / 类型错误；
- 明确 `get_game_screenshot`、YOLO/OCR 调用在失败时的返回/异常约定，并在调用方增加判空 + 兜底逻辑；
- 将与 UI 交互相关的 HTTP 请求迁移到后台线程，增加超时与异常捕获；
- 清理重复的配置函数（以 `core/Config.py` 为唯一配置入口）。

### 阶段 2：接口与服务层重构

- 抽象 `AuthService`、`ConfigService`、`VisionService` 等服务对象，UI 不再直接操作 `requests` 或全局单例；
- 将 `utils/api.py` 中“测试”逻辑迁移到单独文件，正式 API 提供统一返回结构；
- 将全局变量访问集中到一个 `AppEnvironment` 对象中，通过构造注入给线程和服务。

### 阶段 3：刷图核心解耦与模块化

- 逐步拆分 `PlayerThread`：把 YOLO 解析、小地图导航、技能控制分离为独立类；
- 优化地图配置和技能配置的集中管理，减少硬编码与魔法数；
- 在不改变外部行为的前提下，为关键步骤增加日志结构化输出，便于排查。

### 阶段 4：性能与可观测性

- 评估图像识别部分的重复计算与多次截图，尝试做缓存或降低调用频率；
- 为关键路径增加简单的性能指标（单轮刷图耗时、识别耗时、网络往返时间等），输出到日志或 UI。

---

## 九、结语

当前 `front` 代码的功能深度已经远超普通“脚本”，更像一个完整的桌面客户端 + 自动控制系统。  
本优化建议并不是要求一次性重构，而是提供一个**循序渐进的演进路线**：先修明显 bug 和易导致崩溃的问题，再逐步抽象服务层、拆解核心线程、规范配置与输入输出，最终让这个项目在继续添加功能的同时，仍然易于维护和扩展。
